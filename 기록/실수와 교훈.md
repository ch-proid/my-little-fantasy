# 실수와 교훈

같은 실수를 되풀이하지 않으려고 적는다. **작업을 시작할 때 이 문서를 먼저 읽는다.** 새 실수를 하면 바로 아래에 덧붙인다.
적는 법: 무엇을 잘못했나 → 왜 문제인가 → 앞으로 어떻게 하나.

## 대화

### 1. 한국어로 묻는데 영어로 답함 (여러 번)
- **잘못:** 사용자가 한국어로 말하는데 답이나 중간 안내를 영어로 했다. 특히 긴 작업 끝의 보고, 도구를 쓰는 사이사이의 짧은 안내에서 자주 나왔다.
- **왜 문제:** 사용자가 다시 "한국어로 해 주세요"라고 말해야 했다. 읽는 수고와 시간을 뺏는다.
- **앞으로:** 사용자에게 보이는 글은 **모두 한국어**. 보고, 중간 안내("~를 확인합니다"), 질문, 표 모두. 코드 주석과 기록도 한국어. 보내기 전에 한 번 더 본다: 영어 문장이 섞였나?

### 2. 기록을 늦게 남김
- **잘못:** 일을 여러 개 마친 뒤 한꺼번에 기록했다.
- **앞으로:** 결정·변경이 생기면 그 일을 끝내는 즉시 `기록/`에 덧붙인다 (CLAUDE.md 1번 규칙).

## 사용자의 컴퓨터

### 3. 사용자가 다른 일을 할 때 실제 게임 창을 켜고 화면을 찍음
- **잘못:** 사용자가 다른 게임을 하는 중에 게임 창을 새로 띄우고 화면 전체를 찍었다. 사용자의 게임 화면이 찍혔다(바로 지웠다).
- **왜 문제:** 사용자의 작업을 방해하고, 사적인 화면을 볼 수 있다.
- **앞으로:** 확인은 **숨긴 확인용 창**(화면 밖·표시 안 함)에서만 한다. 실제 창을 띄우거나 화면을 찍어야 하면 먼저 묻는다.

### 4. 자동으로 뜨는 창이 앞으로 튀어나와 사용자 입력을 가로챔
- **잘못:** 처음 켤 때 닉네임 창을 열면서 창을 앞으로 끌어왔다.
- **앞으로:** 사용자가 직접 누를 때만 창을 앞으로. 자동으로 여는 창은 앞으로 끌어오지 않는다.

### 5. 저장이 사라질 뻔함: 앱 이름 바꾸기
- **잘못:** 폴더 정리 중 `package.json`의 `name`을 바꿨다. Electron은 이 이름으로 저장 위치(`%APPDATA%\이름`)를 정하므로, 바꾸면 기존 저장이 안 보인다.
- **앞으로:** `package.json`의 `name`은 바꾸지 않는다 (`my-little-fantasy`). 저장 위치·저장 키(`mlf.v2`)에 닿는 것은 바꾸기 전에 영향부터 확인한다.

### 6. 사용자가 고친 파일을 모르고 지나칠 뻔함
- **잘못:** "다듬었어요"라는 말에 새 파일만 찾았다. 사용자는 내가 만든 `에셋/몬스터/` PNG를 직접 고친 것이었다.
- **앞으로:** "고쳤다·다듬었다"고 하면 **최근에 바뀐 파일 전체**(수정 시각)를 먼저 찾는다. 사용자가 손댄 파일은 자동 처리로 바꾸지 않는다.

## 코드

### 7. 이름 겹침
- `window.bar`(창 다리)가 게임의 `bar()` 함수와 겹쳐 게임이 멈췄다 → `taskbar`로 바꿈. 뒤에 다시 `bar`를 쓰면서 `bar()` 함수가 없는 게임 쪽에서만 씀.
- 메뉴 상태 변수 `view`가 게임의 `view`(캔버스)와 겹침 → `mview`.
- CSS `.title`(타이틀 화면)이 장비 설명의 `.title`과 겹쳐 설명 상자가 화면을 다 차지함 → `.titlescreen`.
- **앞으로:** 새 전역 이름·CSS 클래스를 만들기 전에 `grep`으로 이미 있는지 찾는다.

### 8. 일괄 바꾸기가 정의까지 바꿈
- **잘못:** `1 - prog(t, ` → `pulse(t, ` 를 모든 파일에서 바꾸다가 `pulse` 함수 정의 안쪽까지 바꿔 자기 자신을 끝없이 불렀다.
- **앞으로:** 일괄 바꾸기 뒤에는 바꾼 함수의 **정의부**를 꼭 다시 본다. 가능하면 정의는 바꾸기 뒤에 새로 쓴다.

### 9. 바꾸기가 조용히 실패함
- **잘못:** 파이썬 `replace`로 파일 끝을 고쳤는데 문자열이 맞지 않아 아무 일도 안 일어났다. 결과 파일이 덮어써졌다.
- **앞으로:** 바꾸기는 **반드시 "정확히 한 번 찾았는지" 확인**(`assert s.count(a) == 1`)하고 한다. 확인 없이 `replace` 하지 않는다.

### 10. 셸 따옴표 꼬임
- **잘못:** 한글·작은따옴표가 든 긴 파이썬·CSS를 bash heredoc으로 넘기다 여러 번 깨졌다.
- **앞으로:** 길거나 따옴표가 많은 코드는 **Write로 파일을 만든 뒤 실행**한다.

### 11. 원인을 성급히 짐작함
- **잘못:** 새싹 방울 얼굴이 깨졌을 때 격자 문제로 짐작해 두 번 헛손질했다. 진짜 원인은 "배경과 비슷한 색을 배경으로 친 것"이었다.
- **앞으로:** 고치기 전에 중간 결과(단계별 그림)를 보고 원인을 확인한다.

## 그림

### 12. 사용자가 좋아한 방식을 버림
- **잘못:** 첫 게임의 손도트 몬스터를 벡터로 그린 몬스터로 바꿨다가 "이상하다"는 평을 두 번 받았다.
- **앞으로:** 스타일을 크게 바꾸기 전에 작은 시안을 먼저 보여 준다. 사용자가 좋다고 한 것은 기록에 남기고 지킨다.

### 13. 화면 크기 착각
- **잘못:** 150% 배율 화면에서 캔버스를 1배로 그려 글자가 흐렸다. 스크린샷 좌표도 배율 때문에 어긋났다.
- **앞으로:** 캔버스는 `devicePixelRatio`만큼 촘촘히. 화면을 찍을 때는 DPI 인식을 켠다.

### 14. 그림 밀도를 맞추지 않고 에셋을 들여옴
- **잘못:** AI 그림을 1px 칸 그대로 되살려 넣었다. 용사는 2px 칸이라 몬스터만 촘촘하고 복잡해 "그림체가 튄다"는 평을 받았다. 격자도 가로·세로를 따로 잡아 새싹 방울이 세로로 10% 늘어났다.
- **앞으로:** 새 그림을 넣기 전에 용사 옆에 세워 칸 크기·모양 복잡도를 먼저 비교한다. 격자는 가로·세로 크기가 같은지 확인한다. AI 그림은 컨셉으로 쓰고 우리 방식(글자 지도)으로 다시 찍는다.

### 15. 모든 몬스터에 같은 걸음을 씌움
- **잘못:** 슬라임·딱정벌레·그루터기 모두 "발 번갈아 들기" 한 가지로 움직였다. 발 없는 슬라임도 걸어서 어색하다는 평을 받았다.
- **앞으로:** 움직임은 몸 생김새에 맞춘다(슬라임은 통통, 벌레는 사각사각, 큰 놈은 쿵쿵, 새는 날갯짓). 새 몬스터를 넣을 때 `anim.kind`와 부위 위치를 꼭 정하고 프레임을 펼쳐 본다.

### 16. 눈으로 충분히 보지 않고 끝냈다고 보고함
- **잘못:** 움직임 프레임을 한 번 훑어보고 보고했다. 잎이 몸에서 떨어지고, 날개 테두리가 남고, 이빨 자리에 구멍이 나는 것을 놓쳤다.
- **앞으로:** 그림·움직임 작업은 **3번 이상 직접 눈으로 보고 고친 뒤** 보고한다. 1) 프레임을 크게 펼치고 바뀐 칸을 표시해서 보기 2) 표시 없이 보기 3) 실제 게임 크기로 보기. 볼 것: 부위가 떨어지나, 구멍이 나나, 빈 테두리가 남나, 발이 땅에 닿나.

### 17. 손으로 다 그린 그림에 자동 도트 규칙을 씌움
- **잘못:** 선과 명암이 이미 다 그려진 주인공 그림을 자동 규칙(`dotRefine`)에 통과시켰다. 목·손의 안쪽 선이 피부색 계열로 밝혀지며 빨갛게 변했고, 테두리 색도 바뀌었다.
- **앞으로:** 사람이 다듬었거나 원본에서 칸 색을 그대로 뽑은 그림은 칸 색 그대로 칠한다. 자동 규칙은 글자 지도로 새로 찍은 단순한 그림에만 쓴다.
- **덧붙임:** 캐릭터가 하나뿐인 AI 그림은 `도트복원.py`보다 "격자 찾기 → 칸 가운데 색 뽑기"가 낫다. `명암정리.py`는 밝은 재료(머리·피부·셔츠)를 한 색으로 합쳐 버리므로, 사람 캐릭터에는 쓰지 않는다.

### 18. 파일을 덮어쓰기 전에 사용자가 고쳤는지 먼저 보지 않음
- **잘못:** 몬스터 PNG에 여백을 붙이면서, 사용자가 그 사이 PNG를 고쳐 둔 것을 덮어쓴 뒤에야 알았다. 다행히 그림 부분을 그대로 옮겨 붙이는 작업이라 고친 내용은 지켜졌지만, 게임 파일까지 고친 그림으로 바로 다시 만들었다.
- **앞으로:** `에셋/`의 파일을 건드리기 전에, 내가 마지막으로 만든 것과 지금 파일이 같은지 먼저 비교한다(6번과 같은 뿌리). 다르면 사용자가 고친 것으로 보고, 무엇이 바뀌었는지 먼저 알린다. 편집기에서 열려 있을 수 있으니, 덮어쓴 뒤에는 "다시 열어 주세요"라고 알린다.

### 19. 무기마다·몬스터 역할마다 따로 시험하지 않음
- **잘못:** 시험을 늘 섞인 무리로, 빨리 감기로만 돌려서 "칼 용사 + 원거리 몬스터만 남음"에서 진행이 멈추는 것을 사용자가 찾을 때까지 몰랐다.
- **앞으로:** 전투를 고치면 무기 3종(검·엽총·완드) × 몬스터 역할(무리·탱커·원거리·돌격·보스)을 하나씩 세워 끝까지 싸워지는지 본다. 특히 서로 닿는 거리(몬스터 사거리 대 무기 사거리)가 다른 짝을 먼저 본다.

### 20. 사용자가 고친 색을 도구가 몰래 바꿀 뻔함
- **잘못:** 파츠 도구가 팔레트 밖 색을 가장 가까운 팔레트 색으로 바꾸게 되어 있었다. 사용자가 다듬은 옷(장마다 60~90칸)을 그대로 넣었다면 손질한 색이 사라졌다.
- **앞으로:** 사람이 다듬는 에셋을 넣는 도구는 픽셀을 그대로 옮기는 것이 기본이다. 바꿔야 하면 몇 칸을 왜 바꾸는지 먼저 알리고 묻는다. 도구가 "가까운 색으로 바꿈"을 출력하면 그냥 넘기지 말고 멈춰서 본다.

### 21. 숨긴 창 사진만 믿다가 화면 아래를 못 봄
- **잘못:** 확인용 창을 `show: false`로 띄우면 처음 한 번만 그려져서, 내리기·높이 바꾸기 뒤의 사진이 예전 그대로였다. 몇 번을 헛찍었다. 창 배율(setZoomFactor)도 저장소에 남아 다음 실행에 따라왔다.
- **앞으로:** 페이지를 움직여 가며 찍을 때는 게임 시험처럼 화면 밖(x=-3000)에 `show: true`로 띄우고, 저장소(userData)는 매번 새로 만든다. 사진이 바뀌지 않으면 먼저 이것을 의심한다.

### 22. 규칙을 걷기 그림마다 따로 씌워 엽총 걷기가 깨짐
- **잘못:** 엽총 두 손 자세(뒷손 옮기기)를 걷기 그림 한 장 한 장에 씌웠다. 딛는 그림은 몸이 한 칸 내려앉아 있어서, 정해진 줄만 지우는 규칙이 소매 한 칸을 등 쪽에 남겼다. 사용자가 보고 알려 줬다.
- **앞으로:** 자세는 서 있는 그림에 한 번만 입힌다. 걷기는 그 그림을 통째로 옮겨서 만든다. 자세를 바꾸면 걷기 네 장의 윗몸이 기준 자세와 같은지 칸마다 비교한다.

### 23. 빈 그림끼리 비교하고 "같다"고 믿음
- **잘못:** 미리보기 페이지가 오류로 멈춰 빈 캔버스를 찍었다. 그런데 두 사진이 똑같이 비어 있어서 비교가 "같다"로 나왔다.
- **앞으로:** 찍은 그림은 비교하기 전에 비어 있지 않은지(색 수, 크기)부터 본다. 페이지 콘솔 오류도 함께 받아 본다.

### 24. 한 줄짜리 코드 가운데에 주석을 끼워 뒷부분을 주석으로 만듦
- **잘못:** render.js의 한 줄짜리 코드 중간에 `// 설명`을 넣었다. 그 뒤 코드가 모두 주석이 되어 괄호가 어긋났다. 돌리기 전에 `node --check`로 잡았다.
- **앞으로:** 주석은 줄 위에 따로 쓴다. 코드를 고치면 `node --check`로 문법부터 본다.

### 25. 넓은 빛을 점 솎기(디더)로 그려 모기장 무늬가 생김
- **잘못:** 빛번짐을 도트로 바꾸면서 반투명 대신 규칙적인 점 솎기를 썼다. 작은 빛은 괜찮았지만, 스킬의 넓은 빛은 화면 가득 격자 점무늬가 되었다.
- **앞으로:** 넓은 면은 점 솎기 말고 몇 겹의 평평한 도트 띠로 그린다. 새 그리기 방식은 작은 것과 큰 것을 모두 찍어 보고 나서 정한다.

### 26. 새 파일의 함수 이름이 다른 파일 이름과 겹침 (7번 되풀이)
- **잘못:** 새 gear.js에 `tinted`라는 함수를 만들었는데, forge.js에 같은 이름의 `const`가 있었다. gear.js 전체가 읽히지 않았다.
- **앞으로:** 새 전역 이름을 만들면 모든 스크립트의 줄 첫 선언을 모아 겹침을 검사한다(uitest의 이름 검사 한 줄). 새 파일의 이름에는 머리말(gear…)을 붙인다.

### 27. "그림을 못 불러왔다"를 크기로 짐작함
- **잘못:** 아이콘 캔버스가 16칸 이하면 아직 못 불러온 것으로 쳤다. 그런데 잘라 낸 검 아이콘이 15칸이라 빈 네모로 나왔다.
- **앞으로:** 상태는 짐작하지 말고 표시(data-wait)로 넘긴다.

### 28. 게임 창(Electron)에서만 시험하고, 사용자는 브라우저(Edge)로 게임을 함
- **잘못:** 장비 데이터를 로컬 JSON으로 읽고, PNG를 그린 캔버스의 칸 색을 읽었다(아이콘, 그림 내보내기). Electron에서는 되지만, 사용자가 쓰는 Edge(file://)에서는 보안 때문에 둘 다 막혔다. 그래서 처음 고른 무기가 게임에 나오지 않았다. 저장 위치(Edge 로컬 저장소 시각)를 보고서야 알았다.
- **앞으로:**
  - 게임 기능은 Electron과 Edge 둘 다에서 시험한다. Edge는 헤드리스로, 빈 프로필로 띄운다(scratchpad/edgetest/run.mjs).
  - 브라우저에서 로컬 파일 읽기와 PNG 캔버스 읽기를 하지 않는다.
  - 재현이 안 되면 사용자가 어떤 길로 실행하는지부터 확인한다.

### 29. 몬스터 칸 크기를 "결과 크기 범위"에 맞춰 골랐다 (6지역)
- **잘못:** 원본 도트의 실제 칸 크기를 재지 않았다. 대신 결과가 앞 지역 크기 범위(몇 칸 폭)에 들도록 칸 크기를 골랐다. 그래서 격자가 원본과 어긋나 모양이 뭉개졌고, 다시 뽑았다.
- **앞으로:** 먼저 원본 도트 1칸이 몇 px인지 잰다. 그 값으로 뽑은 뒤 크기를 본다. 크기가 범위를 벗어나면 그때 가서 정한다.
